## 第 13 章 · 三类 Agent 会话的脱敏复盘

本章不展示聊天截图，也不复制原始对话。它从 Codex、Claude Code 和 Zcode 的本地历史中提取工程过程，再把任务、文件、标识符和产品信息改写为公开教学场景。

![从本地会话到公开教学案例](assets/diagrams/session-evidence-sanitization.png)

### 13.1 这些案例是怎样脱敏的

| 处理层 | 保留 | 移除或改写 |
|---|---|---|
| 候选定位 | Skill 名、验证词、工具失败信号 | 不做内容公开 |
| 机器脱敏 | 任务顺序与结果标签 | URL、绝对路径、密钥形式、长 ID、hash |
| 人工核对 | 请求→调查→失败→修正→验证的因果 | 项目名、模块名、代码符号、用户原话 |
| 教学合成 | Skill 选择、产物结构、验收方法 | 能反推业务路线、客户、账号或发布状态的信息 |

收集器当时定位了 67 个相关运行：Codex 30、Claude Code 30、Zcode 7。这些数字只说明存在可用的过程样本，不是产品横评，也不是 Skill 成功率。

### 13.2 案例一：Claude Code 的技术报告事实审计

#### 适合谁

这是一个小白到中级的过渡案例。任务不是写代码，但它训练了 AI 协作开发中最重要的基础能力：把「说得很像真的话」拆成可证伪断言。

#### 脱敏任务

一份桌面客户端架构报告已经写完，其中包含模块数量、状态枚举、调度阶段、执行模式和后端能力等具体说法。目标是确认这些说法都有一手代码或配置证据，而不是「读起来合理」。

#### 传统开发者容易怎样做

1. 从头到尾通读报告，凭熟悉感标几个「可能有问题」。
2. 只检查文字流畅度，不检查可证伪的数值和状态。
3. 让 Agent 「仔细检查不要幻觉」，但不指定证据应来自哪里。

这样做的问题是：Agent 会继续用语言理解语言，却没有被迫回到代码事实。

#### Skill 选择

- `research`：对每个断言找拥有答案的一手来源。
- `code-review`：将报告本身的规范问题和事实错误分开。
- `writing-for-agents`：把未来还会漂移的断言改写为指向可核验证据的表述。

#### 可直接使用的脱敏输入

```text
审查这份技术报告的事实准确性，不要先改文风。

1. 先抽取所有可证伪断言，特别是数量、状态、执行阶段、
   公开接口和模块职责。
2. 为每条断言指定拥有答案的一手代码或配置。
3. 实际运行可重复的检查命令，不要只看文件名推断。
4. 输出断言账本：断言、证据、判定、建议改写。
5. 只修正有证据的错误；无法验证的标为未知。
```

#### Agent 行动时间线

| 步骤 | 行动 | 为什么必须这样做 |
|---|---|---|
| 1 | 把报告中具体数字、枚举、阶段名和绝对语句抽成约 16 条断言 | 没有断言单元，就无法一条条证伪 |
| 2 | 为每条断言选定拥有答案的来源 | 文档内部自洽不是证据 |
| 3 | 用命令统计行为、读取枚举、检查分支和后端列表 | 让结论能被第二个人重复 |
| 4 | 对 3 条不一致做精确修正 | 两条数字已漂移，一条流程阶段说得过度 |
| 5 | 再次读回修改段落，确认没有将「未知」改写成「不存在」 | 负向结论需要更强覆盖证据 |

#### 断言账本示例

| 断言 | 证据所有者 | 判定 | 处理 |
|---|---|---|---|
| 调度流程有四个阶段 | 状态定义与调度分支 | 不准确 | 改为当前可观察的五个阶段 |
| 某模块为惟一执行入口 | 公开调用点与路由配置 | 部分成立 | 改为默认入口，并列出例外边界 |
| 所有后端都支持同一能力 | 后端注册与功能开关 | 未知 | 不做否定，添加验证限制 |

#### 本案例不能证明什么

- 不能证明 Claude Code 会自动找到所有幻觉。
- 不能证明 16 条断言覆盖了整份报告。
- 不能用历史命令为当前代码继续背书。

### 13.3 案例二：Zcode 的配置规范化逻辑迁移

#### 适合谁

这是一个中级案例。你已经能让 Agent 改代码，但需要学会在「写入工具失败」、「后台 review 超时」和「语义细节存疑」同时出现时，哪些可以降级，哪些不能略过。

#### 脱敏任务

一套通用模型配置需要在同步时规范化：自定义模式需保留端点和选项，预置模式需移除无效字段。现有逻辑散落在一个辅助函数中，要求将完整语义收口到中央同步处理器，不新建文件。

#### 任务的真正风险

表面上只是「复制几个 if 分支」，真正风险却有四层：

1. 是否覆盖原辅助函数的每个分支；
2. 新位置的输入和原位置是否处于同一生命周期；
3. 「删除字段」与「赋值为 `undefined`」在后续序列化中是否等价；
4. 旧辅助函数是否仍有其他调用者。

#### Skill 选择

- `implement`：任务边界已经确定，按现有结构做最小改动。
- `diagnosing-bugs`：写入工具失败时，先区分环境问题和代码问题。
- `code-review`：实现后按原逻辑逐分支对照，再单独检查任务要求。

#### 可直接使用的脱敏输入

```text
将已有的配置规范化逻辑完整收口到中央同步处理器。

约束：
- 不新建文件，不设计新抽象。
- 先列出原逻辑的全部分支与不变式，再编辑。
- 修改后逐分支双向对照，不能只看类型检查通过。
- 特别核对字段删除和空值在序列化边界的等价性。
- 运行定向类型检查和现有测试，记录实际输出。
```

#### Agent 行动时间线

1. **读取原语义。** 不先写代码，将自定义分支、预置分支、默认值和删除行为列成表。
2. **第一次写入失败。** 工具拒绝了目标路径；这是写入通道问题，不是代码理论被证伪。
3. **第二次写入失败。** 保留原补丁和误差信息，更换为当前环境允许的可审查编辑方式。
4. **完成最小实现。** 只在已指定处理器中合并分支，不新增通用 helper。
5. **运行类型检查。** 结果通过，但这只能证明类型契约。
6. **后台 review 超时。** 不把「没有 review 结果」宣称为「没有问题」；改为当前 Agent 串行做两轴 review。
7. **发现语义差异候选。** 旧逻辑删除字段，新逻辑赋空值。
8. **核对序列化。** 只有在当前序列化边界两者实际输出一致时，才记录为等价；否则必须修复。

#### 降级决策表

| 失败 | 可以降级吗 | 正确动作 |
|---|---|---|
| 某个编辑工具不可用 | 可以 | 换用可审查写入方式，保留同一补丁目标 |
| 后台 review 超时 | 可以 | 改为串行两轴 review，明确无独立 reviewer |
| 类型检查失败 | 不可以 | 修复后重跑，不能用人工目测替代 |
| 原逻辑与新逻辑分支不一致 | 不可以 | 找回丢失分支或获得明确的需求变更 |
| 序列化等价性未核对 | 不可以 | 执行可观察输出对比或增加回归测试 |

#### 本案例不能证明什么

- 工具最终写入成功，不等于实现语义正确。
- 类型检查通过，不等于持久化输出等价。
- 当前序列化器忽略空值，不代表所有后续消费者都忽略。

### 13.4 案例三：Codex 的整仓定位与冲突审计

#### 适合谁

这是一个高阶案例。它不是找一个 bug，而是在文档、运行状态、历史记录和候选方案并存时，建立「谁有权描述当前」的证据层级。

#### 脱敏任务

一个桌面开发工具仓库经历了多轮实验，有当前说明、研究轨道、内容包、运行状态、历史收据和候选方案。用户要求端到端审视整仓定位是否一致，并列出真正冲突。

#### 为什么「全局搜索关键词」不够

搜索可以找到所有「当前」、「完成」、「发布」，但它无法自动告诉你：

- 这句话是当前事实、目标、历史引用还是测试 fixture；
- 一份研究材料是否已经进入可交付包；
- 一份收据证明的是历史发生过，还是当前仍然有效；
- 一个未完成候选是真正阻塞，还是已被新方向取代。

所以审计必须先建权威层级，再做内容对照。

#### Skill 选择

- `research`：找到每类状态的所有者。
- `domain-modeling`：区分「研究轨道」、「交付包」、「运行」和「发布证据」。
- `code-review`：把发现写成有等级、路径和影响的 findings。
- `wayfinder`：将整仓问题拆成可独立决策的证据边界。
- `writing-for-agents`：修正无触发条件的指针和互相竞争的状态文档。

#### 可直接使用的脱敏输入

```text
对当前仓库做只读、端到端的定位与状态冲突审计。

先完成三件事，再判断冲突：
1. 列出哪些表面有权描述当前产品定位、运行状态和发布状态。
2. 区分当前事实、未实现目标、历史记录和研究材料。
3. 对所有否定或穷尽性结论记录覆盖边界。

输出 findings 时只分四类：
- 当前冲突：两个现役权威面描述不一致。
- 过期候选：旧计划仍被写成下一步。
- 历史记录：当时成立，但不应参与当前判断。
- 权威模糊：没有清楚的当前事实所有者。
```

#### 证据层级示例

| 层级 | 能回答的问题 | 不能跨界回答的问题 |
|---|---|---|
| 当前运行状态与新鲜验证 | 现在是否有活跃运行、命令当前是否通过 | 产品应该如何定位 |
| 当前产品说明 | 对外定位、目标用户、公开范围 | 某个历史运行的实际结果 |
| 交付包与收据 | 某一次可交付任务当时包含什么 | 当前分支仍然通过 |
| 研究轨道 | 候选资料、未决问题、可实验方向 | 已经获得生产发布权限 |
| 历史记录 | 过去发生过什么 | 现在仍然如此 |

#### 发现写法示例

```text
[P1] 当前定位面与运行入口对同一能力的状态不一致

证据：当前说明将该能力标为主链，但新鲜运行状态显示无活跃运行，
且发布门槛仍为 blocked。

影响：新会话可能把研究就绪错当为交付就绪。

最小修正：将产品说明改为已有研究候选，并指向真正的运行/发布状态面。
```

#### 本案例不能证明什么

- 无冲突结论不能超过实际枚举的证据面。
- 仓库中有收据不等于当前存在可发布运行。
- 研究材料完整不等于已经形成对外内容或实现计划。

### 13.5 三个案例的横向对照

| 维度 | 报告事实审计 | 配置逻辑迁移 | 整仓定位审计 |
|---|---|---|---|
| 首要风险 | 文档幻觉 | 语义不等价 | 权威层级混乱 |
| 第一个产物 | 可证伪断言账本 | 原逻辑分支/不变式表 | 证据层级与表面清单 |
| 关键反馈 | 代码/配置定向检查 | 类型、测试、序列化输出 | 新鲜运行状态、验证器和覆盖证据 |
| 可接受降级 | 手工串行核对 | 换写入工具、串行 review | 无图工具时用文件列表+定向命令 |
| 不可降级 | 断言到一手证据的映射 | 分支完整性和序列化等价性 | 当前/历史/目标的分层 |
| 完成声明 | 错误断言已修正，未知仍标明 | 定向检查通过，逐分支双向对照完成 | findings 有证据、影响和最小修正，覆盖限制已声明 |

### 13.6 把任意会话改写成可审计实战的模板

```text
目标：
用一句可验收的话描述本次结果。

权威与边界：
- 哪些文件、代码、运行状态拥有答案？
- 哪些决定只能由人做？
- 哪些信息不得进入公开产物？

失败风险：
- 这次任务最可能以哪种方式看似完成却实际失败？

反馈环：
- 哪条命令或哪个可观察现象能在修正前捕获问题？
- 修正后重跑什么？

执行约束：
- 工具失败时可以怎样降级？
- 哪个语义、安全或验证门槛不允许降级？

收据：
- 改了什么？
- 实际运行了什么？
- 证明了什么？
- 仍然不能证明什么？
```

### 13.7 本章验收

- 能把「Agent 说它做完了」改写为「哪个当前证据证明哪个有限结论」。
- 能区分工具通道失败与工程理论被证伪。
- 能为降级路径保留核心方法，而不是用「环境不支持」删掉验证。
- 能在对外复盘时保留因果与教训，同时移除所有可识别的私有项目事实。
