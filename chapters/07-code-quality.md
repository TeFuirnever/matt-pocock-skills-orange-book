## 第 6 章 · 代码不会自己变好：领域语言、深模块与双轴评审

### 6.1 `domain-modeling`：共同语言不是术语装饰

领域语言会直接影响：

- 用户和 Agent 是否在讨论同一件事；
- 文件、变量和函数是否使用一致名称；
- 搜索是否能快速命中；
- 测试描述是否表达真实行为；
- spec 和代码之间是否存在翻译损耗。

`GLOSSARY.md` 应该像词典：每个词一两句话，必要时记录废弃同义词。它不保存实现细节，不承担规格书、scratchpad 或会议纪要的职责。

### 6.2 `codebase-design`：深模块的共享词汇

![Deep Module：把复杂度藏在稳定接口后面](assets/diagrams/deep-module-comparison.png)

这个 Skill 更像设计词典，不是直接执行的流程。它建立一组精确术语：

- module：一组藏在一起、对外只露接口的行为；
- interface：调用方唯一需要知道的部分，越小越好；
- depth：接口背后藏住的复杂度总量，好模块「深」；
- seam：可以挂测试或替换实现的边界；
- adapter：让两种形状对接的转换层；
- leverage：一处改动替代多处重复修改的能力；
- locality：相关决策放得够近，改一处不用翻遍仓库。

核心判断是深度：一个好模块用小接口隐藏大量复杂行为。

#### 删除测试

想象删掉这个模块：

- 如果复杂度也一起消失，它可能只是无价值的传话筒；
- 如果复杂度散落到许多调用方，它确实在集中管理复杂性。

#### 一个适配器不一定构成真实 seam

只有一个实现时，抽象可能只是预测未来。出现两个需要变化的适配器，才说明 seam 真正存在。不要为了可替换性口号提前造接口。

### 6.3 `improve-codebase-architecture`：先做候选调查，不直接大改

这个流程会：

1. 读取 `GLOSSARY.md` 和相关 ADR；
2. 寻找浅模块、泄漏 seam、重复知识和难测试区域；
3. 生成可视化 HTML 候选报告；
4. 让用户选择一个候选；
5. 再用 `grilling` 探索如何加深模块。

它不会在报告阶段直接设计新接口，也不会把每个理论重构都列出来。架构改进必须由当前真实摩擦推动。

示例输入：

```text
/improve-codebase-architecture

最近改动总是卡在 Provider 配置相关的几个模块。
先读 GLOSSARY.md 和 ADR，做候选调查并列出加深机会让我选，不要直接给重构方案。
```

### 6.4 `code-review`：坏味道与规格偏差都要能指向证据

好的 review finding 应该包含：

- 严重级别；
- 具体文件和位置；
- 可触发的支持输入或使用路径；
- 为什么违反标准或规格；
- 最小修复方向；
- 缺少什么测试。

「代码可以更优雅」不是 finding。「删除 Provider 后默认选择仍指向不存在的 id，下一次启动会进入不可恢复状态」才是可行动问题。

### 6.5 合并冲突：保留两侧意图

当前固定版已删除 `resolving-merge-conflicts` 的 Skill 目录；残留的 docs 页面不能作为可安装入口。以下保留为通用工程练习，不再要求调用这个 Skill。

冲突两侧都可能是正确改动。处理每个 hunk 前应该读取：

- 对应 commit 信息；
- PR 或 issue；
- 两边的测试与文档；
- 当前 merge/rebase 的目标。

禁止整批使用 `--ours` 或 `--theirs`。那只能保证语法上快速消除标记，不能保证任何一侧的意图被保留。

冲突解决完成后，要继续完成 merge/rebase，并运行项目的类型检查、测试和格式化。冲突消失不等于合并正确。

#### `retro`：复盘环境，而不是责备一次回答

`retro` 已从实验目录进入 engineering。它检查导航、自动检查、编码规范、常驻指令、工具成本、无效规则与信息访问。先读项目已有 lint/check 和 CI，优先发现未接通或失效的检查；没有 pre-commit 或 CI 护栏本身也值得报告。机械规则应落成确定性检查，只有必须依赖判断的约束才写入编码规范。输出按严重程度排序的改进候选，不能把复盘自动扩大为修改环境的授权。

### 6.6 常见失败

- `GLOSSARY.md` 膨胀成 scratchpad 或会议纪要：它只承担词典职责。
- 只有一个实现就提前造接口：出现第二个需要变化的适配器，seam 才真实存在。
- 在候选调查报告阶段直接设计新接口：架构改进必须由当前真实摩擦推动。
- finding 只写「代码可以更优雅」：不可行动的评论不是 finding。
- 合并冲突整批使用 `--ours` 或 `--theirs`：标记消失不代表任何一侧的意图被保留。

### 6.7 本章验收

- `GLOSSARY.md` 保持词典边界。
- 能用 module、interface、depth、seam 等精确词讨论设计。
- 只有真实摩擦才进入架构候选，不做理论重构。
- review finding 能指向具体行为和证据。
- merge conflict 按两侧意图解决，不整批选边。
