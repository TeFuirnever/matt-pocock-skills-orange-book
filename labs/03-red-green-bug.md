# Lab 3 · 让一个 bug 先变红

**难度：中级**　**预计：60–90 分钟**　**主风险：先改默认值，再声称修复持久化问题**

## 任务

选择一个可重复的小 bug。优先选择“保存后重启失效”“错误状态没有展示”“设置修改未生效”这一类跨边界症状。目标不是尽快改掉它，而是先建立一条修复前会失败、修复后会通过的命令。

## 操作

### 1. 用公共 seam 重现症状

不要直接调用私有 helper，也不要从 UI 截图判断。通过用户可见的设置服务、公开 API、IPC 合约或端到端交互建立最小复现。

写下这句话并让命令证明它：

```text
当 <用户操作> 完成并重建 <公开边界> 后，<可观察结果> 仍应为 <期望值>。
```

### 2. 确认红色

在修改实现前运行目标命令。它必须因为这次症状失败，而不是因为环境、网络或无关测试失败。保存失败输出的简短摘要。

### 3. 每次只验证一个假设

列出不超过四个候选假设。每个假设必须附一个预测：例如“若写入丢失，磁盘记录没有该字段；若读取回退，磁盘存在该字段但读取值错误”。一次只做能区分一个假设的检查。

### 4. 最小修复，再跑同一条命令

只修改被证据指向的最小边界。修复后先重跑同一条命令，确认由红变绿；再运行该区域已有的必要检查。

## 必须留下的产物

- 可重复的症状描述；
- 同一条目标命令的红色与绿色结果；
- 被接受或排除的假设，以及每个结论的证据；
- 一个永久回归测试或等价的自动检查。

## 验收

- 红色发生在修改前；
- 测试穿过真实公共 seam；
- 修复没有把默认值改成期望值来掩盖问题；
- 临时日志和一次性探针已删除；
- 验收引用的是本次运行结果，不是旧聊天里的成功记录。

## 停止条件

同一条命令已绿、回归测试已固化、范围没有扩张时停止。若根因超出当前 ticket，写入发现并退回 Lab 2 更新 spec。
