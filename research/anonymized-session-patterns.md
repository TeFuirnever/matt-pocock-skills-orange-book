# Codex、Claude Code 与 Zcode 会话的脱敏教学模式

## 用途与边界

本文档是橙皮书第 13 章的编辑证据，不是会话存档。它只记录可公开教学的工作流模式，不保留任何项目身份、本机路径、私有代码、内部标识符、用户原话或发布信息。

这些模式能证明「某种 Agent 协作过程在真实会话中出现过」，不能证明：

- 某个私有项目的架构、状态或代码实现；
- 某个 Agent 产品更优或更稳定；
- 某个 Skill 的成功率、故障率或普适效果；
- 历史会话中的验证对当前分支仍然有效。

## 收集方法

1. 使用本地只读收集器扫描三类 Agent 历史。
2. 仅用「Skill 名、工程流程词、验证信号」定位候选会话。
3. 程序层先移除 URL、绝对路径、令牌形式、长标识符与哈希。
4. 人工只读抽样核对因果顺序，不把摘录直接复制到公开仓库。
5. 编写时再做一次场景合成：保留「请求 → 调查 → 失败 → 修正 → 验证」，替换所有项目事实。

## 样本池

收集器在当时的本地历史中找到 67 个匹配运行：Codex 30、Claude Code 30、Zcode 7。结果标签只是定位用的启发式信号，不是效果统计：

| 启发式信号 | 运行数 | 只能怎样理解 |
|---|---:|---|
| 证据不足 | 30 | 摘要没有显示足够的当前验证，不等于任务失败 |
| 出现收据/完成声明 | 20 | 会话包含证据式结论，仍需回读原始命令 |
| 用户纠正 | 6 | 用户曾改变方向或指出误解，适合研究需求边界 |
| 工具失败信号 | 10 | 某个命令、写入或后台步骤没完成，适合研究降级路径 |
| 中止 | 1 | 会话没有足够材料支持后续教学结论 |

这些数字不能相加成「成功/失败率」。一个运行可以同时有工具失败、用户纠正和最终收据。

## 经人工核对的三个模式

### 模式 A：技术报告事实审计

- **会话类型：** Claude Code。
- **脱敏请求：** 审查一份架构报告，防止行数、状态数、执行模式和模块职责被幻觉化。
- **过程：** 从报告中抽取约 16 条可证伪断言，逐条映射到一手代码或配置，运行定向命令后修正 3 处数值/阶段描述。
- **Skill 映射：** `research` + `code-review` + `writing-for-agents`。
- **可迁移教训：** 审文档不应从「通读感觉」开始，而应从「可证伪断言清单」开始。

### 模式 B：集中配置规范化逻辑

- **会话类型：** Zcode。
- **脱敏请求：** 把散落的配置规范化逻辑收口到一个同步处理器，不新建文件。
- **过程：** 先逐分支阅读原辅助函数；多个写入工具失败后更换可用写入路径；运行类型检查；后台 review 超时后改为直接双向对照；额外核对「删除字段」与「赋空值」在序列化边界是否等价。
- **Skill 映射：** `implement` + `diagnosing-bugs` + `code-review`。
- **可迁移教训：** 工具失败可以降级，语义等价检查不能降级。

### 模式 C：整仓定位与冲突审计

- **会话类型：** Codex。
- **脱敏请求：** 对一个桌面开发工具仓库做端到端定位审计，区分当前冲突、过期候选、历史记录和权威层级模糊。
- **过程：** 先锁定只读审计模式和权威层级；枚举文档、内容包与运行状态；使用仓库验证器和代码关系证据；最后把发现分成四类，避免把已完成历史事项当成当前阻塞。
- **Skill 映射：** `research` + `code-review` + `domain-modeling` + `wayfinder`。
- **可迁移教训：** 整仓审计的关键不是找到最多文件，而是先定义什么证据有权描述「当前」。

## 对外写作规则

1. 只写合成后的任务描述，不使用原始 prompt。
2. 只保留流程中的因果节点，不保留私有代码和参数。
3. 产物示例使用通用名称，不使用原项目文件名。
4. 每个案例都写「不能由此证明什么」。
5. 任何可能反推项目身份的细节，即使对教学有趣也不保留。
